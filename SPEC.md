# Plan: Typed quant trading bot for Kalshi BTC markets (paper + production)

## Context
Two rounds of research showed that the edge on Kalshi's BTC binaries (`KXBTCD` hourly ladder, `KXBTC15M`) comes from a **deterministic probability model**, not an LLM: price each strike as P(60-second BRTI average > K), trade only when the edge beats Kalshi's fee (`0.07·P(1−P)` for takers, `0.0175·P(1−P)` for makers), and quote mainly as a maker. Kalshi sells no historical orderbooks, so we have to record our own from day one. Nobody has publicly shown a profitable bot here, so the system has to **prove viability in paper mode before production can trade**.

User decisions:
- Typed Python.
- No LLM anywhere in the decision path.
- Two environments: `paper` (Kalshi demo) and `production` (Kalshi prod).
- GitHub with branch protection, small-commit history and CI/CD.

Assumption: I couldn't identify "jev". I read it as a deterministic, type-checked expected-value model (pydantic v2 + mypy `--strict` + numpy/scipy). If it's a specific library, it plugs into the `model/` layer below without changing the rest.

Per the "build general-purpose" rule, the base layer is **venue- and asset-agnostic**. Kalshi is venue one and BTC is underlying one, so ETH/SOL or Polymarket later means adding config plus an adapter, not rebuilding.

## Project setup
- Create with the `new-project` skill: `~/Developer/python/edgebook` (working name), private GitHub repo via `gh-axi`, Obsidian tracker + dev log.
- Tooling: `uv` (install with `brew install uv`), Python 3.12 pinned, `ruff`, `mypy --strict`, `pytest` + `hypothesis`, `polars` + `pyarrow`, `pydantic-settings`, `structlog`.
- Typed Kalshi client generated from `https://docs.kalshi.com/openapi.yaml` with `openapi-python-client`. The generated code is committed under `src/edgebook/venues/kalshi/_generated/` and regenerated by a script, so spec drift shows up as a diff.

## Architecture (`src/edgebook/`)
| Package | Responsibility |
|---|---|
| `core/` | Domain types: `Prob` (0–1, validated), `Price` (Decimal, from Kalshi's fixed-point dollar strings), `Market`, `OrderBook`, `Order`, `Fill`, `Position`. Fee functions. Venue- and asset-agnostic. |
| `venues/base.py` | `Venue` protocol: `markets()`, `stream_book()`, `place()`, `cancel()`, `positions()`. |
| `venues/kalshi/` | Request signing (RSA-PSS/Ed25519), REST wrapper over the generated client, WebSocket client (orderbook updates, ticker, user fills), token-bucket rate limiter per tier, demo/prod base URLs from config. |
| `feeds/` | Spot WebSocket feeds from the major BRTI constituent exchanges (Coinbase, Kraken, Bitstamp at minimum) feeding a BRTI proxy (median of venues, 1s), plus the Deribit DVOL/option-smile feed. |
| `recorder/` | Writes book deltas, trades and spot ticks to date-partitioned Parquet. Always on in both environments. |
| `model/` | Pure functions only. A volatility forecaster (EWMA + HAR-RV with jump terms) and a pricer giving P(avg₆₀(S_T) > K) via fat-tailed Monte Carlo with a closed-form fast path. Smile sanity check against Deribit. Calibration metrics (Brier, reliability buckets). |
| `strategy/` | Fair value per strike, then edge after fee. Maker quoting (post-only, skewed by inventory), taker only above a threshold, fractional-Kelly sizing. Underlying and series come from config. |
| `risk/` | Hard limits: per-market, per-event and total exposure; daily loss stop; stale-feed guard (no quoting if spot or book data is older than N ms); kill switch (file/env flag); production guard (below). |
| `execution/` | Order manager: placement and cancel-replace, fill reconciliation against `positions()`, idempotent client order IDs. |
| `backtest/` | Replay engine over recorded Parquet using the same `strategy/` + `risk/` code. Models fees and maker queue position. Adapter to run agents on `oddpool/PredictionMarketBench` episodes as a second check. |
| `app/` | Entrypoints: `record`, `paper`, `live`, `backtest`, `report`. Config via `pydantic-settings` (`EDGEBOOK_ENV=paper|production`). |

**Production guard (enforced in code, in addition to CI):** the prod base URL is reachable only when `EDGEBOOK_ENV=production`, `LIVE_TRADING_ENABLED=true`, and a signed-off `viability.json` (written by the `report` command from paper results) shows positive post-fee EV with a 95% CI above zero over at least the configured minimum number of trades. If any check fails, the bot refuses to start.

## Environments
| | `paper` | `production` |
|---|---|---|
| Kalshi API | `external-api.demo.kalshi.co` | `external-api.kalshi.com` |
| Keys | demo API key (GitHub Environment secret) | prod API key (GitHub Environment secret, required reviewer) |
| Deploy trigger | every merge to `main` | GitHub Release tag `v*` + manual approval |
| Trading | on | off until the viability gate passes and the flag is set |

Both environments also record **production market data read-only**, because the demo orderbook isn't realistic. Paper fills are simulated against the real prod book (shadow mode) and demo orders also go through the demo API to test the order plumbing.

Hosting assumption: one small always-on Linux host running two Docker containers (Fly.io machines or a Hetzner VPS). WebSockets need a long-running process, so Vercel/serverless don't fit. The image is built in CI and pushed to GHCR.

## Git and CI/CD
- **Workflow:** trunk-based, small single-purpose PRs into `main`, squash-merge only, linear history, conventional-commit titles.
- **Branch protection on `main`:** PR required, all checks green, branch up to date, no force-push or deletion, conversations resolved. Merge queue on so small PRs don't break `main` when combined.
- **`ci.yml`** (every PR):
  - `ruff check` + `ruff format --check`
  - `mypy --strict`
  - `pytest` with ≥85% coverage on `core/model/strategy/risk`, plus hypothesis property tests: price within [0,1], monotone decreasing in strike, fee never negative, risk never exceeds limits
  - `pip-audit`
  - `openapi` drift check
  - Docker build
- **`backtest.yml`** (nightly + on PRs touching `model/` or `strategy/`): runs a backtest over a fixed recorded-data fixture and fails if PnL or calibration regresses beyond tolerance against the committed baseline.
- **`deploy.yml`:** `main` deploys to the `paper` environment; release tag deploys to `production` (GitHub Environment with a required reviewer and a wait timer).
- Dependabot + CODEOWNERS.

## Milestones (each one a series of small PRs)
1. **Scaffold:** repo, tooling, CI, branch protection, `core/` types + fees with tests.
2. **Kalshi client + recorder:** generated client, signing, WebSocket, rate limiter. Deploy the recorder to the host and start collecting prod BTC books + spot ticks (the longest lead time, so it starts first).
3. **Model:** volatility forecaster + pricer + calibration report run against recorded settlements.
4. **Backtest:** replay engine + PredictionMarketBench adapter. **Go/no-go #1:** positive post-fee EV in backtest, mainly from maker fills.
5. **Paper trading:** strategy + risk + execution in shadow mode and against the demo API for at least 2–4 weeks; daily `report`.
6. **Production:** viability gate passes, then a release tag, then live with small size limits. Scale limits only through config PRs.

## Verification
- `uv run ruff check && uv run mypy --strict src && uv run pytest` pass locally and in CI.
- Signing: authenticated `GET /portfolio/balance` succeeds against demo.
- Recorder: after 1 hour, the Parquet contains continuous book deltas for current `KXBTCD` markets with no sequence gaps, and the BRTI proxy tracks settlement values within a few dollars for settled hours.
- Model: on recorded settlements, reliability buckets fall inside their CIs and Brier beats the market's mid-price.
- Backtest: deterministic, so the same input gives an identical PnL. PredictionMarketBench `KXBTCD-26JAN2017` episode runs end to end.
- Paper: demo orders place, fill and reconcile; the kill switch cancels all resting orders within one second; the bot refuses to start in production without the gate.
